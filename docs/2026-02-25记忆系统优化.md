# 2026-02-25记忆系统优化

## 背景

当前 AI 使用方式仍偏“即时问答工具”，上下文记忆依赖单次会话，容易出现：

- 每次对话重复交代背景
- 跨渠道（Web GUI / Feishu）上下文串扰
- AI 对长期目标、项目阶段、个人偏好理解不稳定
- 输出质量受当前窗口上下文长度影响较大

本方案目标是将 AI 从“工具”升级为“个人基础设施”，通过结构化文档 + 规则 + 渠道分层，构建可维护、可追溯、可升级的记忆系统。

## 可借鉴思路（提炼）

基于外部案例（Claude Code + Obsidian / PAI / TELOS 类方法）的可借鉴点：

- 将 AI 视为长期运行的基础设施，而不是一次性聊天工具
- 将个人上下文外置为结构化文档，而不是单一超长提示词
- 用多个主题文件建模“你是谁、你在做什么、如何决策”
- 用版本控制管理记忆内容（可追溯、可回滚）
- 让 AI 行为可编程（通过 skill / 规则文件约束读取与写入）

## 方案目标

### 主要目标

- 提升 AI 对个人长期上下文的稳定理解
- 减少重复输入背景信息的成本
- 降低跨渠道会话污染风险
- 让记忆内容可维护、可审计、可迭代

### 非目标

- 不追求“自动记住所有聊天内容”
- 不将敏感凭据写入记忆系统
- 不依赖单一模型厂商的内建记忆能力

## 总体设计

采用三层结构：

1. **记忆数据层（Markdown 文档）**

- 以多个结构化 `.md` 文件保存长期信息
- 使用 Git 版本管理

2. **记忆规则层（Skill / 操作约束）**

- 规定 AI 何时读取哪些文件
- 规定什么信息允许写回、如何写回
- 控制写回频率与格式

3. **交互渠道层（Feishu / Web GUI）**

- Feishu：轻交互、提醒、问答
- Web GUI：重任务、代码分析、配置变更
- 会话隔离避免上下文串扰（已采用 `per-channel-peer` 思路）

## 最小可用版本（MVP）

建议先从 5 个核心文件开始，而不是一次做“10+ 文件”。

### 建议目录（示例）

```text
personal-context/
  00-identity.md
  01-current-focus.md
  02-projects.md
  03-working-rules.md
  04-decision-log.md
```

### 文件职责

#### `00-identity.md`

记录长期稳定信息：

- 角色/背景
- 主要工作领域
- 价值偏好（简版）
- 沟通偏好（语言、风格、输出偏好）

#### `01-current-focus.md`

记录当前阶段（短周期）：

- 当前最优先事项（1-3项）
- 本周目标
- 正在推进的关键问题
- 暂缓事项（避免 AI 误推进）

#### `02-projects.md`

记录项目清单与状态：

- 项目名称
- 当前阶段
- 下一步动作
- 风险/阻塞
- 关联资料位置（仓库、文档、目录）

#### `03-working-rules.md`

记录个人工作规则与约束：

- 对 AI 的使用边界（哪些可自动做，哪些必须确认）
- 输出格式偏好
- 命名规范
- 提交/测试/部署习惯

#### `04-decision-log.md`

记录关键决策（可追溯）：

- 日期
- 决策事项
- 结论
- 原因
- 后续影响

## 与 OpenClaw 的集成设计

## 1. 读取策略（Read Path）

不同任务读取不同记忆文件，避免每次全量加载。

### 推荐读取策略

- 日常问答（Feishu）
  - 读取：`01-current-focus.md` + `03-working-rules.md`
- 项目相关讨论
  - 读取：`02-projects.md` + `01-current-focus.md`
- 决策建议/复盘
  - 读取：`04-decision-log.md` + `03-working-rules.md`
- 首次建立上下文/长期规划
  - 读取：`00-identity.md` + `01-current-focus.md` + `02-projects.md`

原则：

- 默认按需读取，不做全量注入
- 优先读取“当前焦点”和“工作规则”
- 长期身份信息低频读取

## 2. 写回策略（Write Path）

AI 不应随意改写长期记忆，建议采用“建议写回”或“受控写回”。

### 建议写回规则

- 允许 AI 提议新增内容，但默认不自动写入核心身份信息
- `04-decision-log.md` 可作为首个受控写回目标（最适合）
- 写回内容必须结构化（日期 + 决策 + 原因）
- 单次写回应小而明确，避免大段改写

### 不建议自动写回的内容

- 凭据、令牌、账号信息
- 高敏感个人隐私
- 未确认的事实判断

### 写回确认等级（建议补充）

为避免“记忆污染”，建议给写回操作分级：

- `L0（无需写回）`
  - 普通问答、临时讨论、未定结论
- `L1（建议写回，先确认）`
  - 新的阶段性目标、项目状态变化、明确结论
- `L2（可自动写回，低风险）`
  - 仅在用户明确授权的场景，且目标文件为 `04-decision-log.md`
- `L3（必须人工确认）`
  - 涉及身份定义、工作规则、长期目标的修改

## 3. 渠道分层策略（Channel Segmentation）

为了兼顾便利性与安全性，建议对渠道分工：

### Feishu（外部即时消息）

适合：

- 轻问答
- 任务提醒
- 快速确认
- 状态查询

不适合：

- 大量本地文件读取
- 高风险命令执行
- 复杂调试与配置变更

### Web GUI（本地控制台）

适合：

- 代码分析
- 文件编辑
- 配置变更
- 调试与排障

## 4. 会话隔离策略（避免串扰）

核心原则：

- 不同渠道 / 不同联系人 / 不同任务类型尽量使用独立会话
- 避免将排障上下文带入日常问答场景

已验证有效的思路（可继续保持）：

- `per-channel-peer` 类型的会话隔离策略

## 5. 记忆冲突与优先级策略（新增）

当“当前对话”和“记忆文件”冲突时，需要明确优先级，避免 AI 自作主张。

### 信息优先级（建议）

1. **用户当前明确指令（本轮）**
2. **用户本轮确认的新事实**
3. **`01-current-focus.md`（当前阶段）**
4. **`02-projects.md` / `04-decision-log.md`**
5. **`00-identity.md`（长期背景）**

### 冲突处理原则

- 不要静默覆盖旧记忆
- 发现冲突时，先指出冲突点，再按当前指令执行
- 若用户确认变更，再写回对应记忆文件

示例：

- 记忆里写“本周重点是 A”，但用户本轮说“现在优先做 B”
  - 回答时应以 `B` 为准
  - 并建议更新 `01-current-focus.md`

## 6. 时效性与过期治理（新增）

记忆系统的常见失败点不是“没有记忆”，而是“记忆过期”。

### 建议增加的字段（各文件）

- `最后更新日期`
- `适用周期`（如：长期 / 本周 / 当前项目阶段）

### 过期判断建议

- `01-current-focus.md`
  - 超过 7-14 天未更新时，默认视为“可能过期”
- `02-projects.md`
  - 项目状态长期不变时，需确认是否已搁置/完成
- `03-working-rules.md`
  - 低频更新，但发生工作流程变化时要及时更新

### AI 使用时的保守策略

- 若发现“最后更新日期”为空或过旧：
  - 允许使用，但需降低置信度
  - 在回答末尾提示“建议刷新记忆文件”

## 安全与风险控制

记忆系统会提升 AI 的“理解能力”，同时也会扩大误用影响面，因此必须加边界。

### 风险点

- 记忆文档包含过多敏感信息
- 外部渠道触发本地 `exec/read/browser`
- AI 将内部诊断信息回发给终端用户
- 自动写回导致记忆污染

### 控制措施

- 记忆文档只存“对协作有用”的信息，不存凭据
- 渠道分层（Feishu 轻交互，Web GUI 重操作）
- 保留配对/授权策略（如 DM pairing）
- 关键操作仍需人工确认
- 对外回复做内容清洗（避免 reasoning / 内部诊断泄露）

### 额外补充（容易忽略）

- 记忆文件本身也属于敏感资产（尤其 `projects.md` / `decision-log.md`）
- 建议纳入 Git，但避免同步到公开仓库
- 若使用云盘/笔记同步，先确认同步目标的隐私边界

## 记忆文件格式规范（新增）

为了让 AI 更稳定地读取/更新，建议统一格式。

### 基础规范

- 文件名固定（如 `00-identity.md`）
- 标题层级稳定（避免频繁重命名一级标题）
- 使用明确字段标签（如“最后更新日期：”）
- 尽量使用列表和短段落，避免超长自由文本

### 为什么需要格式规范

- 降低 AI 读取/更新时误改概率
- 便于后续写校验脚本/自动化工具
- 便于 diff 审阅和版本追踪

## 版本治理与回滚（新增）

记忆系统本质是“可演化配置”，需要版本治理。

### 建议做法

- 每次重要记忆更新形成独立 commit（尤其 `decision-log` 批量补录时）
- 将“模板调整”和“内容更新”分开提交
- 出现明显记忆污染时，优先回滚文件而不是继续叠加修补

### Git 提交建议（示例）

- `Memory: refresh current focus and project states`
- `Memory: record decision on OpenClaw custom upgrade workflow`
- `Memory: refine working rules for Feishu channel`

## 验收标准

满足以下条件可视为一期完成：

- 日常问答时不需要反复解释当前重点
- AI 能正确引用当前项目状态与下一步动作
- Feishu 与 Web GUI 的上下文不再明显串扰
- 决策类输出可沉淀到 `decision-log`
- 记忆文档变更可通过 Git 查看历史

### 建议增加的可观测指标（补充）

- 需要重复解释背景的频次是否下降
- AI 引用错误/过期项目状态的频次是否下降
- `decision-log` 的沉淀频率是否稳定（例如每周 >= N 条）
- 记忆文件更新滞后（例如 `current-focus` 超过 14 天未更新）

## 结论

本方案的核心不是“让 AI 记住更多”，而是：

- 让**重要信息有结构**
- 让**读取/写入有规则**
- 让**渠道使用有边界**
- 让**上下文演化可追踪**

这比单纯增加提示词长度更稳定，也更适合长期维护。
