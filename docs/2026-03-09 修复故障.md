# 2026-03-09 修复故障

## 状态

- 提议中。
- 当前文档只整理需求、根因、技术方案、测试范围和待决策项。
- 当前文档不包含代码改动，也不直接改变现有配置语义。

## 需求摘要

这次修复的目标不是单纯把超时时间调大，而是让超长私聊 session 在接近上下文极限时仍然满足以下要求：

- 本轮消息已经生成的最终回复，不能再被 compaction 长时间阻塞。
- active run 被卡住时，后续消息不能只停留在进程内存里。
- gateway 重启、session reset、health monitor 恢复后，后续消息必须可恢复，不能无声丢失。
- 长期私聊的连续性要保留，但应由 memory、summary、session rotate 承担，而不是无限膨胀单个 transcript。

## 事故背景

2026-03-08 19:44 CST，这条 Feishu 私聊 lane 出现 compaction timeout，随后用户看到的现象是：

- 后续消息已经进入网关。
- 但没有形成可发出的最终回复。
- lane 被单个旧 session 长时间占住，直到 health monitor 重启和 session reset 才解除。

结合日志和 session transcript，可以确认这是一次典型的“超长 session + compaction 卡 lane + followup 内存态丢失”故障，而不是单纯的外部消息发送接口失败。

## 根因总结

### 主因

1. 单条 DM session 长期不 rotate，旧 transcript 已经进入高风险区。
2. prompt 完成后，run 仍然等待 compaction，导致 lane 不释放。
3. 后续消息在 active run 期间进入 followup queue，但 followup queue 只有内存态。
4. session reset 或 gateway 重启前，这些 followup 没有被转成可恢复任务。

### 放大因素

1. 当前默认 queue mode 是 `collect`，active run 存在时，后续消息天然会先进入 followup。
2. `memory flush` 只做预处理，并不会主动 rotate session。
3. `resetSession()` 会把旧 session 的部分运行态统计字段直接继承给新 session，容易污染后续观测和阈值判断：
   - `src/auto-reply/reply/agent-runner.ts`

### 非主因

- 没有找到和 `2026-03-08 19:44 CST` 严格对应的 Feishu outbound 发送失败证据。
- 因此，这次故障的主因不是“final reply 已生成但发送失败”，而是“final reply / followup 没有走完完整处理链路”。

## 目标

- 让超长 DM session 在接近上下文上限时主动切换到新 session，而不是继续在旧 session 上赌 compaction 成功。
- 让本轮最终回复尽量早于 compaction 完成发出。
- 让后续消息在 active run 卡住时仍然可恢复。
- 让运维和状态面板可以直接看出 session 是否处于 compaction 风险状态。

## 非目标

- 不在这一轮重写 Pi compaction 引擎本身。
- 不在这一轮重做所有 queue mode 的语义。
- 不在这一轮改造 Feishu channel 的传输层协议。
- 不在这一轮追求“所有中断中的工具执行都能完美恢复”。

## 当前实现观察

### 1. DM 历史裁剪能力存在，但未作为主要防线使用

当前运行时已经支持 `dmHistoryLimit`，会在真正送模型前对历史 user turn 做截断：

- `src/agents/pi-embedded-runner/history.ts`
- `src/agents/pi-embedded-runner/run/attempt.ts`
- `src/agents/pi-embedded-runner/compact.ts`

但这只是送模型前的局部裁剪，不等价于：

- 旧 transcript rotate
- followup durable
- compaction timeout 隔离

因此它只能降低风险，不能根治这次故障链路。

### 2. delivery queue 的 durability 位置太靠后

当前 outbound delivery queue 的持久化点在 final payload 生成之后：

- `src/infra/outbound/deliver.ts`

这意味着：

- 如果 reply payload 还没有形成，delivery queue 根本还没参与。
- 本次事故里真正缺失的是“待执行 followup turn 的 durability”，而不是“待发送 final payload 的 durability”。

### 3. compaction 与 final reply 仍处于同一条 run 生命周期中

当前实现虽然在等待 compaction 前尝试 flush block reply，但 lane 仍然会继续等：

- `src/agents/pi-embedded-runner/run/attempt.ts`

这会导致两件事绑定在一起：

- 本轮回复何时结束
- 旧 session 的 compaction 是否顺利完成

这正是需要拆开的核心点。

## 技术方案

建议分 4 个工作流推进，优先级按 P1 -> P4。

### P1. Session Pressure Gate：对高风险 DM 主动 rotate

#### 目标

在进入 agent run 之前，识别“这条 DM session 已不适合继续在旧 transcript 上运行”，直接切到新 session。

#### 核心思路

复用当前 `memory flush` 已经具备的 transcript 读取能力，在 run 前增加一层 `session pressure` 判定：

- transcript prompt tokens
- transcript bytes
- projected next-input size
- 最近 compaction timeout 次数

如果命中硬阈值，则不再尝试继续复用旧 session，而是：

1. 创建新 `sessionId`
2. 继承必要的会话元信息
3. 清空运行态 token 统计
4. 将当前用户 turn 直接在新 session 中执行

#### 推荐触发条件

建议使用混合阈值，而不是单一 `totalTokens`：

- `projectedTokenCount >= contextWindow - reserveTokensFloor - rotateSoftMargin`
- `transcriptByteSize >= rotateTranscriptBytes`
- `recentCompactionTimeoutCount > 0` 且在短时间窗口内再次收到消息

#### 连续性保留方式

推荐默认采用：

- 新 session fresh start
- continuity 由 memory / summary carryover 承担

不推荐默认将旧 transcript 的最近若干原文大段搬入新 session，因为这会把新 session 很快重新养胖。

#### 推荐落点

- `src/auto-reply/reply/agent-runner-memory.ts`
- `src/auto-reply/reply/agent-runner.ts`
- `src/config/sessions/types.ts`

#### 新增状态建议

建议在 `SessionEntry` 增加：

- `recentCompactionTimeoutAt`
- `recentCompactionTimeoutCount`
- `autoRotatedAt`
- `autoRotatedReason`
- `sessionPressureState`

### P2. Compaction Breaker：将 final reply 与 compaction 解耦

#### 目标

让“本轮最终回复可交付”不再依赖“旧 session compaction 最终成功”。

#### 核心思路

当前全局 run timeout 是 10 分钟，但 post-prompt compaction 不应继续占满整个 lane。

建议引入独立的 `postPromptCompactionGraceMs`：

- prompt 完成后，最多只等一个较短的 compaction grace period
- 如果 grace period 内 compaction 未完成：
  - 用 pre-compaction snapshot 作为本轮结果基准
  - 标记该 session 为 compaction unhealthy
  - 尽快释放 lane
  - 让后续消息自动进入新 session

#### 行为原则

- 已经拿到的 final text 应优先交付。
- compaction 是旧 session 的 housekeeping，不应无限阻塞同一 DM lane。
- 旧 session compaction 可被中止或降级为 best effort。

#### 推荐落点

- `src/agents/pi-embedded-runner/run/attempt.ts`
- `src/agents/pi-embedded-subscribe.ts`
- `src/auto-reply/reply/agent-runner-execution.ts`

### P3. Durable Followup Queue：把 followup 从内存队列升级为可恢复队列

#### 目标

让 active run 期间进来的后续消息，在 gateway 重启或 session reset 后仍然可以恢复。

#### 当前问题

followup queue 目前是纯内存 `Map`：

- `src/auto-reply/reply/queue/state.ts`

而且只有当前 run finalize 后才会 drain：

- `src/auto-reply/reply/agent-runner-helpers.ts`
- `src/auto-reply/reply/queue/drain.ts`

因此只要 active run 卡在 compaction，后续消息就会落在不可恢复窗口内。

#### 推荐实现

参照现有 outbound delivery queue 的 write-ahead 模式，新建 followup persistence：

1. `enqueueFollowupRun()` 先落盘，再放入内存 queue。
2. drain 成功后 ack。
3. gateway 启动时恢复未完成 followup。
4. session rotate 时，把未处理 followup 迁移到新 session。

#### 持久化对象建议

推荐不要直接把整个运行期 config 快照原样复制到磁盘，而是定义一版 `PersistentFollowupEntry`，只保留恢复真正需要的字段：

- `prompt`
- `messageId`
- `summaryLine`
- `originatingChannel / To / AccountId / ThreadId`
- `sessionKey / sessionId / sessionFile`
- `agentId / agentDir / workspaceDir`
- `provider / model`
- thinking / verbose / reasoning / elevated
- auth profile / owner / extraSystemPrompt

运行时 config、skills snapshot 则在恢复时用当前配置重建。

这样更容易：

- 做 schema 版本管理
- 避免把过大的 config 重复写入磁盘
- 降低恢复时使用过期配置的概率

#### 推荐落点

- `src/auto-reply/reply/queue/enqueue.ts`
- `src/auto-reply/reply/queue/state.ts`
- `src/auto-reply/reply/queue/drain.ts`
- 新增 `src/auto-reply/reply/queue/persistence.ts`
- gateway 启动恢复路径

### P4. Session Reset Hygiene：切新 session 时清理运行态污染

#### 目标

让新 session 的状态反映新 transcript 的真实体量，而不是沿用旧 session 已失效的 token 统计。

#### 当前问题

`resetSession()` 当前是基于旧 `SessionEntry` 直接 spread 出新 entry：

- `src/auto-reply/reply/agent-runner.ts`

这会把上一条 session 的运行态数据继续带给新 session，例如：

- `inputTokens`
- `outputTokens`
- `totalTokens`
- `cacheRead`
- `cacheWrite`
- `compactionCount`
- `memoryFlushAt`
- `memoryFlushCompactionCount`

这会造成两个问题：

1. 新 session 的观测数据看上去“天生很胖”。
2. 后续基于这些字段做阈值判断时，可能被旧值污染。

#### 建议

切新 session 时只保留用户级、路由级、行为级配置，不保留运行态体量统计。

## 临时止血建议

在正式实现 P1-P4 之前，建议先做两项保守止血：

1. 给这条高风险 Feishu DM 单独配置 `dmHistoryLimit`
2. 提高 `agents.defaults.compaction.reserveTokensFloor`

这两项不能根治 followup durability 问题，但可以显著降低：

- 超长 transcript 继续膨胀
- compaction 进入极端高压区

## 配置建议

### 短期止血

建议先在配置层支持：

- 对 Feishu DM 的 per-DM `historyLimit`
- 更保守的 `reserveTokensFloor`

### 中期新增配置

建议新增一组 session pressure / rotate 配置，例如：

```yaml
agents:
  defaults:
    compaction:
      rotateOnPressure:
        enabled: true
        projectedTokenMargin: 12000
        transcriptBytes: 8388608
        recentTimeoutWindowMinutes: 30
        recentTimeoutThreshold: 1
      postPromptCompactionGraceMs: 8000
```

配置名可以再讨论，但需要表达两类语义：

- 什么时候应该主动切 session
- prompt 结束后最多愿意等 compaction 多久

## 测试计划

建议至少补以下测试：

### 1. 主动 rotate

- 长 DM session 命中 pressure gate 后，当前 turn 应直接在新 session 运行。
- 新 session 不应继承旧 session 的 token 统计字段。
- continuity summary / memory carryover 行为应符合预期。

### 2. compaction breaker

- prompt 成功、compaction 长时间未结束时，应仍然返回 final payload。
- lane 应在 grace period 后释放，而不是继续等到总 timeout。
- 后续消息应能进入新 session，而不是继续被旧 lane 卡住。

### 3. durable followup

- active run 期间收到多条 followup，重启后应能恢复并继续处理。
- session rotate 后，旧 followup 应迁移到新 session。
- 去重规则仍应以 `messageId + routing metadata` 为主。

### 4. 兼容性

- `collect`
- `followup`
- `steer-backlog`

三种 queue mode 下都要覆盖。

### 5. 回归验证

- Feishu direct DM
- 其他默认 `collect` 的 channel
- block streaming disabled 场景
- routeReply / delivery queue 现有行为不回退

## 上线顺序

### 第一阶段：止血

- 先上 per-DM `dmHistoryLimit`
- 提高 compaction reserve

### 第二阶段：结构修复

- 上 `postPromptCompactionGraceMs`
- 上 session pressure rotate

### 第三阶段：durability

- 上 durable followup queue
- 增加启动恢复和 rotate 迁移

### 第四阶段：可观测性

- session status 增加 compaction unhealthy / recent timeout / auto-rotated 展示
- diagnostics 增加相应字段和计数

## 验收标准

- 旧 session 即使 compaction 超时，也不会再把同一 DM lane 卡到无法继续处理后续消息。
- 后续消息在 active run 被占用期间进入 durable queue，重启或 reset 后仍可恢复。
- 已经形成的 final reply 不再必须等待旧 session compaction 成功。
- 新 session 不再继承旧 session 的运行态 token 污染。
- 高风险 DM session 会在进入危险区之前主动 rotate。

## 待决策项

### 1. 连续性保留策略

推荐：

- fresh session
- continuity 由 memory / summary carryover 承担

可选但不推荐默认开启：

- 直接带最近 N 轮原文进入新 session

### 2. durable followup 的持久化粒度

推荐：

- 定义 `PersistentFollowupEntry`
- 持久化恢复所需最小字段
- 恢复时重建当前 config / skills snapshot

备选：

- 直接持久化完整 `FollowupRun`

### 3. 默认 DM queue 行为是否调整

推荐：

- 保持默认 `collect`
- 通过 durable queue 解决 reliability

备选：

- 针对单条高风险 DM 改为 `interrupt`

这会提升响应速度，但会改变长任务执行语义。

## 结论

这次故障不是单点 bug，而是 3 个设计假设同时失效：

1. 超长 DM session 仍然继续复用旧 transcript。
2. final reply 与 compaction 被绑定在同一 run 生命周期中。
3. followup queue 没有 durability。

因此，修复也不应只停留在“调大超时”或“补一个 reset”。推荐路径是：

- 先止血
- 再做 session pressure rotate + compaction breaker
- 最后补 durable followup queue

这三步做完后，才能从结构上消除“旧 session 膨胀 -> compaction 卡 lane -> 后续消息丢失”的链路。
