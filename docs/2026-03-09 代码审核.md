## 背景

2026-03-09 的代码审核聚焦在 Telegram 入站链路的一致性问题。当前实现里，普通消息、native command、reaction、reply media 并没有完全共享同一套路由和上下文规则，导致在特定 Telegram 交付场景下，同一个用户的会话可能被拆成多个 session，或者 reply 引用已经被识别但媒体上下文没有真正带入。

本轮确认的 3 个问题如下：

1. `src/telegram/bot-native-commands.ts`
   - native command 的 DM 路由仍然直接使用 `String(chatId)`。
   - 普通消息路径已经改为优先使用 `senderId`。
   - 在 Telegram business / bridge 等 `chat.id != sender.id` 的场景下，slash command 会命中不同的 route/session。

2. `src/telegram/bot-handlers.ts`
   - reaction 事件在 DM 下仍然直接使用 `String(chatId)`。
   - 这会让 reaction 和普通消息进入不同 session。

3. `src/telegram/bot-handlers.ts`
   - `hasReplyTargetMedia()` 已经把 `reply_to_message ?? external_reply` 视为 reply target。
   - `resolveReplyMediaForMessage()` 仍然只读取 `reply_to_message`。
   - 结果是外部引用回复可以通过“有回复媒体”的判断，但拿不到真实的 `replyMedia`。

## 当前实现观察

- `src/telegram/bot-message-context.ts`
  - 普通消息在 DM 下已经使用 `resolveTelegramDirectPeerId({ chatId, senderId })`。
- `src/telegram/bot-native-commands.ts`
  - `resolveCommandRuntimeContext()` 仍然在 DM 下使用 `String(chatId)`。
- `src/telegram/bot-handlers.ts`
  - reaction 路径仍然在 DM 下使用 `String(chatId)`。
  - `hasReplyTargetMedia()` 和 `resolveReplyMediaForMessage()` 对 reply target 的定义不一致。
- `src/telegram/bot/helpers.ts`
  - 已经存在 `resolveTelegramDirectPeerId()`、`buildTelegramGroupPeerId()`、`describeReplyTarget()` 等基础 helper。
  - 这里适合继续收口共享路由和 reply target 解析逻辑。

## 目标

- 统一 Telegram DM 的路由主键，使普通消息、native command、reaction 命中同一 session。
- 统一 Telegram reply target 的解析，使 `reply_to_message` 和 `external_reply` 在文本与媒体上下文上保持一致。
- 用共享 helper 消除分叉实现，降低后续回归风险。
- 为上述行为补充稳定的回归测试。

## 非目标

- 不调整 callback / inline button 的授权语义。
- 不重做 Telegram forum topic 或 DM topic 的整体 session 设计。
- 不修改 ACP 绑定策略。
- 不引入配置 schema 变化或存储迁移。
- 不在这一轮扩展到 album 级别的 reply media 还原。

## 建议统一的语义

### 1. DM 路由

- DM `peerId` 规则：`senderId || chatId`
- 也就是优先使用真实发送者 id；只有缺失时才回退到 `chatId`

### 2. 群组路由

- group `peerId` 规则：`chatId[:topic]`
- forum topic 继续沿用 `buildTelegramGroupPeerId(chatId, resolvedThreadId)`

### 3. 群组父级 peer

- 只有 forum topic 场景继续保留 base `chatId` 作为 `parentPeer`
- 本轮不改变现有父级 peer 继承逻辑

### 4. Reply target

- reply target 统一定义为：`reply_to_message ?? external_reply`
- 文本引用、媒体判断、媒体提取都必须基于同一个 resolved target

### 5. `external_reply` 支持范围

- 第一轮只做到与当前 `resolveInboundMediaFileId()` 能力一致
- 也就是先保证单条媒体消息行为正确，不扩展到更复杂的多媒体集合恢复

## 技术方案

### 方案总览

本轮不建议只在 3 个点打补丁，而是建议抽出共享 helper，然后替换普通消息、native command、reaction、reply media 路径的分叉逻辑。这样可以把“路由主键规则”和“reply target 规则”收口成单一事实来源。

### 1. 在 `src/telegram/bot/helpers.ts` 增加共享 helper

建议新增两个高层 helper：

- `resolveTelegramRoutingPeerId(params)`
  - 输入建议包含：
    - `isGroup`
    - `chatId`
    - `resolvedThreadId`
    - `senderId`
  - 规则：
    - group: `buildTelegramGroupPeerId(chatId, resolvedThreadId)`
    - DM: `resolveTelegramDirectPeerId({ chatId, senderId })`

- `resolveTelegramReplyTargetMessage(msg)`
  - 返回：
    - `msg.reply_to_message ?? msg.external_reply`

建议保留现有 `resolveTelegramDirectPeerId()` 和 `buildTelegramGroupPeerId()`，把它们作为更低层的组合部件，而不是直接替换掉。

### 2. 调整 `src/telegram/bot-message-context.ts`

`buildTelegramMessageContext()` 当前在行为上已经是正确的，但仍然建议改为调用 `resolveTelegramRoutingPeerId()`，原因如下：

- 让普通消息路径成为共享实现的一部分，而不是继续保留内联逻辑。
- 后续如果 Telegram DM 路由规则再调整，只改 helper 即可。
- 可以明确 `bot-message-context.ts` 依赖的不是“拼接规则”，而是“统一路由约定”。

这一步应保持行为不变，不触碰：

- `threadSpec`
- `threadIdForConfig`
- `parentPeer`
- topic override 的 route/sessionKey 重算逻辑

### 3. 调整 `src/telegram/bot-native-commands.ts`

`resolveCommandRuntimeContext()` 需要改为使用共享路由 helper，并传入 `msg.from?.id` 作为 DM sender 候选值。

本轮只建议改这一层：

- `peerId`
- 由 `peerId` 派生的 route / configured route / session key 结果

本轮不建议扩大到：

- native command 的授权语义
- `parentConversationId`
- 其他与绑定/ACP 相关的行为

### 4. 调整 `src/telegram/bot-handlers.ts`

这里建议分为两部分：

#### reaction 路由统一

- reaction 路径改为调用 `resolveTelegramRoutingPeerId()`
- 在 DM 下与普通消息、native command 保持同一主键

保留当前边界：

- reaction 仍然只做 chat-level forum 处理
- 不尝试在本轮补齐 Telegram API 没有提供的 `message_thread_id` 信息

#### reply target 统一

- `hasReplyTargetMedia()` 改为调用 `resolveTelegramReplyTargetMessage()`
- `resolveReplyMediaForMessage()` 也改为调用 `resolveTelegramReplyTargetMessage()`
- 这样“是否有 reply 媒体”和“真正解析 reply 媒体”就使用同一份 reply target

### 5. 测试方案

本轮建议补 3 组回归测试：

- native command 路由一致性
  - 在 `chat.id != from.id` 的 DM 场景下
  - 断言 native command 与普通消息命中同一 route/session

- reaction 路由一致性
  - 在同样的 DM 场景下
  - 断言 reaction 事件进入和普通消息一致的 sessionKey

- `external_reply` 媒体一致性
  - 构造带媒体的 `external_reply`
  - 断言 `replyMedia` 能真正进入消息处理链路，而不仅仅是通过 gating

建议优先补在这些测试文件中：

- `src/telegram/bot-native-commands.test.ts`
- `src/telegram/bot.test.ts`
- `src/telegram/bot/helpers.test.ts`

如果共享 helper 的抽象影响到既有 DM 线程行为，也可以补充或复用：

- `src/telegram/bot-message-context.dm-threads.test.ts`

## 建议执行顺序

1. 在 `src/telegram/bot/helpers.ts` 新增共享 helper。
2. 将 `src/telegram/bot-message-context.ts` 切换到共享 helper，确保基线行为不变。
3. 修改 `src/telegram/bot-native-commands.ts` 和 `src/telegram/bot-handlers.ts` 的分叉逻辑。
4. 补齐 `native command`、`reaction`、`external_reply media` 三类回归测试。
5. 跑 Telegram 相关测试，再跑一次完整测试或至少相关回归集合。

## 验收标准

- 普通消息、native command、reaction 在 DM 下使用相同的会话主键规则。
- `chat.id != sender.id` 的 Telegram business / bridge 场景下，不再出现 session 分裂。

- 普通 `reply_to_message` 行为不回退。
- 既有 forum topic 和 group session 路由行为不发生意外变化。

## 待决策项

### 1. 修复方式

待确认：

- 采用“3 个调用点最小修补”
- 或采用“共享 helper 收口”

建议：

- 采用“共享 helper 收口”

原因：

- 当前问题本质上是规则分叉，而不是单点逻辑错误。
- 如果继续只修调用点，后续新增入口仍然容易再次偏离。

### 2. `external_reply` 媒体支持深度

待确认：

- 只做与当前单消息媒体提取能力对齐
- 或进一步扩到更复杂的引用媒体恢复

建议：

- 第一轮只做单消息媒体对齐

原因：

- 可以直接修复本轮回归。
- 风险和验证范围更可控。

### 3. 是否顺手处理 callback / inline button 语义

待确认：

- 本轮只修路由与 reply target
- 或顺手把 callback 相关 allowlist 语义一起整理

建议：

- 本轮不要顺手处理

原因：

- callback/allowlist 是相邻但不同类的问题。
- 混入同一 patch 会扩大行为面和测试面。

## 风险说明

- 如果共享 helper 的命名或职责边界不清，可能把低层工具函数和高层路由约定混在一起，反而增加维护成本。
- 如果测试只覆盖 helper，不覆盖实际消息处理链路，可能仍然漏掉 route/session 级别的回归。
- 如果本轮顺手修改 callback 授权语义，容易让 patch 目标失焦，增加 reviewer 判断成本。

## 结论

Telegram 范围已经按“共享 helper 收口 + 小范围调用点替换 + 回归测试补齐”的方式完成实施。该方案在不扩大配置和授权语义范围的前提下，修复了 Telegram DM 路由分叉和 `external_reply` 媒体上下文缺失的问题，并补齐了相应回归测试。仓库其余大范围改动需要作为下一阶段单独审查。
