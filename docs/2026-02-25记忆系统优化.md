# 2026-02-25记忆系统优化

## 背景

当前 AI 使用方式仍偏“即时问答工具”，上下文记忆依赖单次会话，容易出现：

- 每次对话重复交代背景
- 跨渠道（Web GUI / Feishu）上下文串扰
- AI 对长期目标、项目阶段、个人偏好理解不稳定
- 输出质量受当前窗口上下文长度影响较大

本方案目标是将 AI 从“工具”升级为“个人基础设施”，通过结构化文档 + 规则 + 渠道分层，构建可维护、可追溯、可升级的记忆系统。

## 可借鉴思路（提炼）

基于外部案例（Claude Code + Obsidian / PAI / TELOS 类方法）的可借鉴点：

- 将 AI 视为长期运行的基础设施，而不是一次性聊天工具
- 将个人上下文外置为结构化文档，而不是单一超长提示词
- 用多个主题文件建模“你是谁、你在做什么、如何决策”
- 用版本控制管理记忆内容（可追溯、可回滚）
- 让 AI 行为可编程（通过 skill / 规则文件约束读取与写入）

## 方案目标

### 主要目标

- 提升 AI 对个人长期上下文的稳定理解
- 减少重复输入背景信息的成本
- 降低跨渠道会话污染风险
- 让记忆内容可维护、可审计、可迭代

### 非目标

- 不追求“自动记住所有聊天内容”
- 不将敏感凭据写入记忆系统
- 不依赖单一模型厂商的内建记忆能力

## 总体设计

采用三层结构：

1. **记忆数据层（Markdown 文档）**

- 以多个结构化 `.md` 文件保存长期信息
- 使用 Git 版本管理

2. **记忆规则层（Skill / 操作约束）**

- 规定 AI 何时读取哪些文件
- 规定什么信息允许写回、如何写回
- 控制写回频率与格式

3. **交互渠道层（Feishu / Web GUI）**

- Feishu：轻交互、提醒、问答
- Web GUI：重任务、代码分析、配置变更
- 会话隔离避免上下文串扰（已采用 `per-channel-peer` 思路）

## 最小可用版本（MVP）

建议先从 5 个核心文件开始，而不是一次做“10+ 文件”。

### 建议目录（示例）

```text
personal-context/
  00-identity.md
  01-current-focus.md
  02-projects.md
  03-working-rules.md
  04-decision-log.md
```

### 文件职责

#### `00-identity.md`

记录长期稳定信息：

- 角色/背景
- 主要工作领域
- 价值偏好（简版）
- 沟通偏好（语言、风格、输出偏好）

#### `01-current-focus.md`

记录当前阶段（短周期）：

- 当前最优先事项（1-3项）
- 本周目标
- 正在推进的关键问题
- 暂缓事项（避免 AI 误推进）

#### `02-projects.md`

记录项目清单与状态：

- 项目名称
- 当前阶段
- 下一步动作
- 风险/阻塞
- 关联资料位置（仓库、文档、目录）

#### `03-working-rules.md`

记录个人工作规则与约束：

- 对 AI 的使用边界（哪些可自动做，哪些必须确认）
- 输出格式偏好
- 命名规范
- 提交/测试/部署习惯

#### `04-decision-log.md`

记录关键决策（可追溯）：

- 日期
- 决策事项
- 结论
- 原因
- 后续影响

## 与 OpenClaw 的集成设计

## 1. 读取策略（Read Path）

不同任务读取不同记忆文件，避免每次全量加载。

### 推荐读取策略

- 日常问答（Feishu）
  - 读取：`01-current-focus.md` + `03-working-rules.md`
- 项目相关讨论
  - 读取：`02-projects.md` + `01-current-focus.md`
- 决策建议/复盘
  - 读取：`04-decision-log.md` + `03-working-rules.md`
- 首次建立上下文/长期规划
  - 读取：`00-identity.md` + `01-current-focus.md` + `02-projects.md`

原则：

- 默认按需读取，不做全量注入
- 优先读取“当前焦点”和“工作规则”
- 长期身份信息低频读取

## 2. 写回策略（Write Path）

AI 不应随意改写长期记忆，建议采用“建议写回”或“受控写回”。

### 建议写回规则

- 允许 AI 提议新增内容，但默认不自动写入核心身份信息
- `04-decision-log.md` 可作为首个受控写回目标（最适合）
- 写回内容必须结构化（日期 + 决策 + 原因）
- 单次写回应小而明确，避免大段改写

### 不建议自动写回的内容

- 凭据、令牌、账号信息
- 高敏感个人隐私
- 未确认的事实判断

### 写回确认等级（建议补充）

为避免“记忆污染”，建议给写回操作分级：

- `L0（无需写回）`
  - 普通问答、临时讨论、未定结论
- `L1（建议写回，先确认）`
  - 新的阶段性目标、项目状态变化、明确结论
- `L2（可自动写回，低风险）`
  - 仅在用户明确授权的场景，且目标文件为 `04-decision-log.md`
- `L3（必须人工确认）`
  - 涉及身份定义、工作规则、长期目标的修改

## 3. 渠道分层策略（Channel Segmentation）

为了兼顾便利性与安全性，建议对渠道分工：

### Feishu（外部即时消息）

适合：

- 轻问答
- 任务提醒
- 快速确认
- 状态查询

不适合：

- 大量本地文件读取
- 高风险命令执行
- 复杂调试与配置变更

### Web GUI（本地控制台）

适合：

- 代码分析
- 文件编辑
- 配置变更
- 调试与排障

## 4. 会话隔离策略（避免串扰）

核心原则：

- 不同渠道 / 不同联系人 / 不同任务类型尽量使用独立会话
- 避免将排障上下文带入日常问答场景

已验证有效的思路（可继续保持）：

- `per-channel-peer` 类型的会话隔离策略

## 5. 记忆冲突与优先级策略（新增）

当“当前对话”和“记忆文件”冲突时，需要明确优先级，避免 AI 自作主张。

### 信息优先级（建议）

1. **用户当前明确指令（本轮）**
2. **用户本轮确认的新事实**
3. **`01-current-focus.md`（当前阶段）**
4. **`02-projects.md` / `04-decision-log.md`**
5. **`00-identity.md`（长期背景）**

### 冲突处理原则

- 不要静默覆盖旧记忆
- 发现冲突时，先指出冲突点，再按当前指令执行
- 若用户确认变更，再写回对应记忆文件

示例：

- 记忆里写“本周重点是 A”，但用户本轮说“现在优先做 B”
  - 回答时应以 `B` 为准
  - 并建议更新 `01-current-focus.md`

## 6. 时效性与过期治理（新增）

记忆系统的常见失败点不是“没有记忆”，而是“记忆过期”。

### 建议增加的字段（各文件）

- `最后更新日期`
- `适用周期`（如：长期 / 本周 / 当前项目阶段）

### 过期判断建议

- `01-current-focus.md`
  - 超过 7-14 天未更新时，默认视为“可能过期”
- `02-projects.md`
  - 项目状态长期不变时，需确认是否已搁置/完成
- `03-working-rules.md`
  - 低频更新，但发生工作流程变化时要及时更新

### AI 使用时的保守策略

- 若发现“最后更新日期”为空或过旧：
  - 允许使用，但需降低置信度
  - 在回答末尾提示“建议刷新记忆文件”

## 安全与风险控制

记忆系统会提升 AI 的“理解能力”，同时也会扩大误用影响面，因此必须加边界。

### 风险点

- 记忆文档包含过多敏感信息
- 外部渠道触发本地 `exec/read/browser`
- AI 将内部诊断信息回发给终端用户
- 自动写回导致记忆污染

### 控制措施

- 记忆文档只存“对协作有用”的信息，不存凭据
- 渠道分层（Feishu 轻交互，Web GUI 重操作）
- 保留配对/授权策略（如 DM pairing）
- 关键操作仍需人工确认
- 对外回复做内容清洗（避免 reasoning / 内部诊断泄露）

### 额外补充（容易忽略）

- 记忆文件本身也属于敏感资产（尤其 `projects.md` / `decision-log.md`）
- 建议纳入 Git，但避免同步到公开仓库
- 若使用云盘/笔记同步，先确认同步目标的隐私边界

## 记忆文件格式规范（新增）

为了让 AI 更稳定地读取/更新，建议统一格式。

### 基础规范

- 文件名固定（如 `00-identity.md`）
- 标题层级稳定（避免频繁重命名一级标题）
- 使用明确字段标签（如“最后更新日期：”）
- 尽量使用列表和短段落，避免超长自由文本

### 为什么需要格式规范

- 降低 AI 读取/更新时误改概率
- 便于后续写校验脚本/自动化工具
- 便于 diff 审阅和版本追踪

## 版本治理与回滚（新增）

记忆系统本质是“可演化配置”，需要版本治理。

### 建议做法

- 每次重要记忆更新形成独立 commit（尤其 `decision-log` 批量补录时）
- 将“模板调整”和“内容更新”分开提交
- 出现明显记忆污染时，优先回滚文件而不是继续叠加修补

### Git 提交建议（示例）

- `Memory: refresh current focus and project states`
- `Memory: record decision on OpenClaw custom upgrade workflow`
- `Memory: refine working rules for Feishu channel`

### 推荐开发顺序（降低返工版）

建议按以下顺序推进，优先稳定“结构与边界”，再做自动化和检索：

1. **三层记忆架构（先做接口和最小实现）**

2. **用户档案（落到 Semantic Memory）**

- 目标：把现有 `personal-context/*.md` 从“模板”升级为可被程序稳定读取的结构化语义实体
- 建议先做：字段约束、分区规范、解析器
- 预期产出：Profile / Projects / Rules 的结构化解析与校验

3. **Skills 系统（可组合能力模块）**

- 目标：把“读取记忆 / 生成写回建议 / 写入决策日志”封装成可组合能力
- 建议先做：`load-context`、`propose-memory-write`、`commit-decision-log`
- 预期产出：可复用 skill 约定 + 调用模板（先手动触发也可）

4. **Hooks 系统（会话前后自动化）**

- 目标：在会话前自动加载必要记忆，在会话后生成写回建议或受控写回
- 建议先做：`pre-session`（读）+ `post-session`（建议写回，不自动改核心文件）
- 预期产出：Hook 配置、触发条件、失败降级策略、日志可观测性

5. **知识索引（语义搜索）**

- 目标：在记忆规模变大后提升召回能力与检索效率
- 建议先做：关键词/规则检索兜底，再接向量索引（如 `sqlite-vec`）
- 预期产出：`memory search` 接口、召回排序、索引刷新策略

- 检查“最后更新日期”是否缺失/为空/明显过期（按文件类型阈值）
- `memory:add-decision` 用于结构化追加决策日志条目（支持 `--dry-run` 预览）
- `memory:apply-suggestion` 用于受控执行 L2 `decision-log` 写回建议（需提供结构化 suggestion JSON）

- `memory:suggestions` 用于查看/应用/忽略建议队列（适合非 Web GUI 场景人工确认）

  - 外部渠道（如 Feishu / Telegram）现已支持消息内文本命令（不需要切 CLI）：
    - `记忆建议 列表`
    - `记忆应用 pms_xxx`
    - `记忆忽略 pms_xxx`
    - 英文等价：`memory suggestions` / `memory apply pms_xxx` / `memory dismiss pms_xxx`
  - **新增：Feishu 原生按钮式确认（p2p 场景）**
    - post-session 生成队列项后，会额外发送“记忆建议卡片”（Apply / Dismiss）
    - 点击按钮会直接执行队列动作（无需再输入文本命令）
    - 若卡片发送或回调失败，会自动回退到文本说明 + 文本命令路径（不中断主回复）
  - Feishu 触发 `L2 decision-log` 的前提（当前实现）：
    - 消息命中 `decision-review` 任务类型（如包含“决策/方案/取舍/review”等）
    - 消息包含显式确认语句（如“我确认/确认采用/就按这个方案执行/I confirm ...”）
    - 消息包含结构化字段（至少 `决策标题`、`背景`、`决策`、`原因`）
  - 推荐 Feishu 测试格式（多行发送）：
    - 第一行写确认语句 + 意图（例如“我确认采用这个方案，请记录决策并给出下一步实施计划”）
    - 后续各行使用 `字段名：内容`（如 `决策标题：...` / `背景：...` / `决策：...` / `原因：...`）
- `memory:gc` 用于清理 runtime memory 与建议队列历史项（支持 `--dry-run`）
- `memory:archive` 用于归档旧决策（将超出保留期的主 `decision-log` 条目移动到 archive 文件，支持 `--dry-run`）
- `memory:archive-runtime` 用于归档过期 runtime `episodic` 记录到 `personal-context/archive/runtime-episodic.archive.jsonl`（支持 `--dry-run`）
- `memory:migrate-legacy` 用于将工作区内旧 Markdown 迁移到 `personal-context`：
  - `decision-log`：结构化导入决策记录（按 `日期 + 标题` 去重）
  - `projects`：优先结构化迁移项目状态（解析 Markdown 表格或 `## 项目名` 分节，导入到 `## 历史迁移项目状态（结构化）`）；无法解析时回退快照导入
    - 可选 `--merge-project-overview`：将解析出的项目状态按项目名 upsert 到 `02-projects.md` 的 `项目清单（总览）` 表（默认关闭，避免误覆盖）
    - `--merge-project-overview` 仅支持 `--target-kind projects`；其他目标会显式报错
  - `current-focus/identity/working-rules`：快照导入到 `## 历史迁移快照` 区域（按来源+日期标题去重）
  - 支持 `--target-kind`、`--dry-run`
- `memory:share-runtime` 用于跨工作区导出/导入 runtime memory（MVP）：
  - 默认导出/导入 `episodic`（`working` 需显式 `--include-working`）
  - 用于跨实例分享近期运行时上下文（支持 `--dry-run`）
  - `sync` 模式可对本地 runtime 与 bundle 做双向收敛（写回 runtime + 刷新 bundle）
  - `import/sync` 会输出冲突统计（同 `id` 记录胜负），并可写入 `--audit-file` JSONL 审计日志
  - 支持 `--conflict-strategy latest|current|incoming` 控制 `id` 冲突时的胜出策略（默认 `latest`）
- `memory:status` 用于查看 personal-memory 三层快照状态与计数
- `memory:status` 会同时显示 personal-memory settings 来源、渠道开关摘要与 runtime GC 摘要
- `memory:search` 用于检索记忆内容（支持 `keyword / hybrid / semantic` 模式、layer 过滤）
  - `semantic/hybrid` 默认使用 `.semantic-index-cache.json` 做持久化语义向量缓存（sparse-cache，可用 `--no-cache` 关闭）
  - 默认启用 `hybrid-v2` 二阶段重排（可用 `--no-rerank` 关闭，也可切回 `mmr-lite`）
  - 可通过 `--rerank-top-k` 或 `channels.<channel>.search.rerankTopK` 调整重排候选池大小
  - 可通过 `--rerank-strategy hybrid-v2|mmr-lite` 或 `channels.<channel>.search.rerankStrategy` 指定策略
  - 可选 `sqlite-vec` 后端（新增）：
    - CLI：`pnpm memory:search --query "..." --mode semantic --backend sqlite-vec`
    - settings：`channels.<channel>.search.backend = "sqlite-vec"`
    - 可选 `sqliteVecFile` / `sqliteVecExtensionPath`
    - 若 `sqlite-vec` 不可用，会自动降级到 sparse-cache，并在 `cache.reason` 标记 `sqlite-vec-fallback:*`
- `memory:summary` 用于查看最近决策摘要，便于复盘和引用
- `memory:touch` 用于批量刷新记忆文件“最后更新日期”

## 验收标准

满足以下条件可视为一期完成：

- 日常问答时不需要反复解释当前重点
- AI 能正确引用当前项目状态与下一步动作
- Feishu 与 Web GUI 的上下文不再明显串扰
- 决策类输出可沉淀到 `decision-log`
- 记忆文档变更可通过 Git 查看历史

### 建议增加的可观测指标（补充）

- 需要重复解释背景的频次是否下降
- AI 引用错误/过期项目状态的频次是否下降
- `decision-log` 的沉淀频率是否稳定（例如每周 >= N 条）
- 记忆文件更新滞后（例如 `current-focus` 超过 14 天未更新）

## 结论

本方案的核心不是“让 AI 记住更多”，而是：

- 让**重要信息有结构**
- 让**读取/写入有规则**
- 让**渠道使用有边界**
- 让**上下文演化可追踪**

这比单纯增加提示词长度更稳定，也更适合长期维护。
